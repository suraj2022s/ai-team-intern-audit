# Part C — Decision memo: casual/conversational tone in Hindi, Kannada, Tamil, Telugu, Bengali, Marathi

**Recommendation: (b) a small (≤1B) inference-time rewriter**, trained via
self-distillation on the A100 (no external API needed), with **(c)
prompt-engineering shipped immediately as a day-1/day-2 stopgap** while (b)
trains — not a hedge between two paths, but a staged rollout with an
explicit kill criterion that falls back to (c) alone if (b) underperforms.

## Assumptions

- The main assistant model is already deployed and can be prompted (via the
  team's own infra, not an external API) to generate synthetic
  "casualize this response" pairs — this is how "no external API budget" is
  satisfied for data generation.
- A ≤1B rewriter sitting after the main model is materially easier to
  gate, roll back, and evaluate per-language than fine-tuning the main
  model directly (SFT path (a)), which is the deciding factor given the
  reviewer-coverage gap below.
- The binding constraint on this project is **reviewer coverage, not
  compute**: we have a human check for only 2 of 6 target languages
  (Hindi, Kannada). Tamil, Telugu, Bengali, Marathi ship with no native
  human QA at all under any path. That risk has to be managed explicitly,
  not assumed away.

## Back-of-envelope arithmetic

- **Data volume**: target ~3,000 synthetic (formal-response → casual-rewrite)
  pairs per language × 6 languages = **~18,000 pairs**, generated by
  few-shot prompting the main model. At a rough batched-generation rate of
  ~50k tokens/min on the A100 and ~150 tokens/pair average, generating the
  full set is ~2.7M tokens ≈ **under an hour** of raw generation compute —
  not the bottleneck.
- **Training cost**: ≤1B model, 3 epochs over ~18k-54k (with augmentation)
  examples, batch 32 → ~1,700-5,000 steps. On a single A100-80GB this is a
  **few hours**, not days. Out of the 2-week (336h) A100 budget, this
  leaves the large majority of the time for data-generation iteration,
  hyperparameter sweeps, and re-training after reviewer feedback — compute
  is not the constraint here either.
- **Reviewer throughput**: 10h/week × 3 weeks = **30 reviewer-hours**,
  Hindi + Kannada only. At ~1.5 min per blind pairwise judgment (formal
  output vs. rewriter output, thumbs up/down + note), that's **~1,200
  judgments total, ~600 per language** — enough for a win-rate estimate
  with a ~±4pp confidence interval. This reviewer budget is spent on two
  things: (1) directly validating the rewriter on the 2 covered languages,
  (2) calibrating a cheap automatic "casualness" proxy (informality-marker
  heuristic or small classifier) that we then apply, with lower trust, to
  the 4 uncovered languages.

## Success metric (numeric threshold)

**≥65% human pairwise win-rate** for rewriter output vs. original formal
output, on the Hindi+Kannada reviewer sample (~600 judgments/language),
**and** the automatic casualness proxy shows a positive delta over baseline
on all 6 languages, **and** meaning-distortion/hallucination flags stay
**≤3%** of the reviewed sample.

## Kill criterion

**By day 10 of the 3-week window**: if Hindi/Kannada human win-rate is
**below 55%** (not clearly beating the formal baseline) **or**
meaning-distortion is flagged in **more than 5%** of the reviewed sample,
kill path (b). Fall back to shipping (c) prompt-engineering-only for the
day-21 launch review — it's already live from day 1, so "killing" (b) costs
nothing but the sunk A100/reviewer time already spent, not launch
readiness.

**Latency guardrail (third kill trigger)**: (b) runs the rewriter
*sequentially after* the main model, which necessarily adds latency — and
latency works directly against the product goal of a "casual and
conversational" feel, so this needs its own check, not just win-rate and
hallucination rate. No target latency is given in the assignment materials,
so this is a number to confirm with product, not assume — but a
conversational reply is a tighter bar than general UI responsiveness:
natural human turn-taking gaps run **~200-300ms**, well under the ~1s
threshold usually cited for "keeps the user's flow of thought" in
general-purpose UI (Nielsen's response-time heuristics), so that's the
wrong anchor here — a sequential rewriter pass is competing with
conversational cadence, not page-load patience. Day 1 measures the main
model's current end-to-end p50/p95 response time as a baseline (see Day-1
experiment below), and as soon as a first rewriter checkpoint exists — per
the training-cost arithmetic above, that's within the first few days, well
before the day-10 checkpoint — we measure its added latency on top of that
baseline. **Provisional trigger**: if the rewriter adds more than
**~300ms** on top of the baseline (subject to whatever bar product actually
confirms), treat that as a kill trigger for (b) on the same day-10
timeline, same fallback to (c).

## Day-1 experiment

Two things run in parallel on day 1, before committing further budget:
1. Generate ~50-100 self-distilled casual/formal pairs per language via
   few-shot prompting the main model; manually eyeball a sample across all
   6 languages (not reviewer time — just a sanity check) to confirm
   self-distillation isn't producing degenerate or nonsensical output
   before spending A100 hours training on it.
2. Same-day A/B a casual system-prompt (path (c)) against current formal
   outputs on a handful of examples per language, to get an immediate,
   cheap read on how far prompting alone moves the needle — this becomes
   both the day-1 stopgap and the baseline that (b) has to beat.
3. Measure the main model's current end-to-end p50/p95 response latency in
   production as a baseline. This is the number the rewriter's added latency
   gets compared against once a checkpoint exists (see Kill criterion) — no
   point defining a latency kill trigger without first knowing what "normal"
   response time is today.

## Biggest caveat (connects back to Part A)

This is the same shape of problem as A1's corpus caveat: a benchmark or
review process that only covers a subset of what you're shipping has to be
reasoned about explicitly, not treated as representative. Four of six
target languages ship without any native-speaker check under every path on
the table, including this recommendation — the automatic casualness proxy
is a mitigation, not a substitute, and should be flagged to leadership as a
residual risk at launch, not silently absorbed.
